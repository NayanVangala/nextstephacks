## Premise challenge — what this review changed

The plan being executed before this review was "keep improving the codebase."
That plan does not win this. Judging is a video under five minutes, a written
submission, and maybe sixty seconds on the live link. The day this review ran
produced five shipped fixes, a twelve-finding design audit, a fourteen-finding
architecture review and 130 green tests. None of it touched anything a judge
is scored against.

Three gaps found in the audit, none of them code:

1. **No video.** Hard submission requirement. Does not exist in the repo.
2. **No README**, on a public repo, with `homepageUrl` empty — so a judge who
   clicks through to GitHub sees a bare file tree with no link to the live demo.
3. **Theme fit.** "Earth Forward" is a climate hackathon. The string appears
   exactly once in the entire product: the landing footer. If a judge reads this
   as an accessibility project that mentions heat, it scores badly on theme.

The framing that fixes (3), and which the data already proves: **climate
adaptation is unequally distributed, and this measures the gap.** Heat is the
hazard, disability is who it lands on hardest. That is a climate project.

## Vision

### 10x check

Passable has been treated as a routing tool. It is not. It is the only thing
that computes, per disability profile and per hour, **who cannot get where in a
heat event** — a number that exists nowhere in public data and is currently
thrown away when the browser tab closes.

The 10x version publishes it. **The Passable Index:** for every block group in
each city, at 2pm on a design day, what share of the step-free network is
reachable, how much is shaded, and how many cooling centres fall inside a
wheelchair user's heat budget. Ranked worst-first.

A routing tool helps one person at a time. An index is evidence a city can be
held to.

### Platonic ideal

Someone opens Passable at 1:40pm in July. It already knows it is 39°C. It does
not hand them a search box — it says *"Here are the three places you can reach
and get back from before your budget runs out."* An answer, not a form.

When they find something wrong, they say so, and the next person's route bends
around it. The map gets better because people walked it.

A second door onto the same engine: a planner sees which blocks go unreachable
at 2pm, ranked. The individual and the institution reading the same truth from
the same graph.

### Phoenix reframe (D4.9)

The recommendation was to cut Phoenix: building heights are published for 6% of
downtown, and the *refusal to ship it* is currently one of three findings on the
landing page and the most credible thing the project says.

The user overrode this. The reframe that makes the override stronger than the
original position: do not ship Phoenix quietly. Ship it **with its uncertainty on
the surface** — "this is what a city looks like when the data is not there." The
`纹-low` hatch pattern already exists for exactly this purpose. Phoenix stops
being a hole in the credibility story and becomes a live demonstration of the
uncertainty design system. A judge sees hatching everywhere and understands the
thesis without being told.

**Condition:** the 94%-inferred figure must be as prominent in Phoenix as the
8%-inferred figure currently is in LA. If it is not, the override does trade
credibility for coverage.

**Critical gaps: 4.** Each is a case where the failure is silent and untested. The
governing rule for all four: if the Index is absent or partial, the view must say so
rather than render empty and look like zero — the same discipline already applied to
the missing GTFS wheelchair field.

## Performance notes

- Index precompute runs reach() per block group. LA has roughly 2,500 block groups at
  ~30ms each, so **~75s of pipeline time per city per profile.** Fine as a build step.
  Must never run client-side.
- T4 (memoize adjacency + largest component) is REQUIRED, not deferred: D4.3 runs the
  route cost function across 8 hour buckets, which is 224ms without it.
